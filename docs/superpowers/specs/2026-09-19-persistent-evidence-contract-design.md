# B1.1 持久化证据与结构化结论设计

日期：2026-09-19
状态：用户已确认，待实施计划复核
前置阶段：B1 证据校验影子模式

## 1. 背景

B1 已证明证据校验器能够读取真实 run、生成幂等校验记录、跨 Gateway 重启保存结果，并且手动重放不会新增模型调用。但 T001 v3 的旧运行事件使用 `memory` 后端，重启后搜索、页面和工具记录无法恢复；原回答也没有稳定的 Claim/Evidence 结构，因此真实记录只能诚实返回 `not_evaluable`。

B1.1 的目标不是扩大样本量或直接判断所有事实真假，而是先让系统拥有可持续保存、可定位和可复核的证据输入。

## 2. 已确认的产品目标

面向启用 `evidence-research-v1` 的证据研究任务：

1. 搜索、网页、工具和最终回答事件写入持久化存储，Gateway 重启后仍可读取。
2. 用户看到正常可读的研究报告，重要结论旁显示可点击的“来源 N”标签。
3. 同一次研究运行产出机器可读的 Claim/Evidence 候选关系，不额外调用第二个评分模型。
4. 系统用真实运行事件核对 Agent 提交的来源，不能相信模型自报的搜索数、页面数、Token、延迟或访问事实。
5. 自动校验只做影子观察，不修改原回答、不改变 run 状态、不自动发布。
6. 数据不完整或无法判断时返回明确的数据缺口，不伪造通过。

## 3. 本阶段非目标

- 不实现全量普通聊天的证据模式。
- 不实现第二模型评分或事后模型抽取。
- 不实现自动发布、人工审批写接口或生产硬门禁。
- 不运行 T002，不批量生成付费样本。
- 不迁移已经随内存丢失的历史 run events。
- 不预设 Claim、Evidence、摘录或 Token 的产品硬上限。
- 不声称单个真实样本能够证明准确率、用户价值或生产稳定性。

现有平台级安全限制和数据库字段限制继续生效。若内容因平台限制被截断，必须记录数据缺口，不能把截断内容解释为“证据不存在”。

## 4. 方案比较与选择

### 方案 A：从普通回答事后解析

优点是改动小；缺点是系统需要从自由文本猜测结论、证据和对应关系，无法稳定满足可定位要求。否决。

### 方案 B：回答完成后调用第二个模型抽取

优点是接入直接；缺点是增加调用、Token、费用和延迟，第二个模型仍可能产生幻觉。B1.1 不采用。

### 方案 C：同一研究运行提交结构化结果

模型在完成研究时，通过仅对证据质量配置开放的结构化结束入口，一次提交可见报告与 Claim/Evidence 候选。结束入口直接返回可见报告，不再触发评分模型；系统随后使用运行记录做确定性核对。

选择方案 C。实现计划必须用可观测测试证明：结构化结束入口之后没有为了质检再次调用模型；不能只凭代码推断“零额外调用”。

## 5. 用户体验

最终报告保持 Markdown，可见引用使用 DeerFlow 已支持的格式：

```markdown
Deep Research 会执行多步骤网页研究。[citation:来源1](https://example.com/source)
```

现有前端会把它渲染成引用标签：

- 鼠标悬停显示来源域名和网址；
- 点击后在新标签页打开来源；
- 使用 `noopener noreferrer`；
- 普通外部链接仍按原有方式显示。

用户不需要阅读后台 JSON。Claim ID、Evidence ID 和核对状态主要服务于质检卡与人工复核。

## 6. 总体数据流

1. 用户创建 run，并在现有 run metadata 中提交 `quality_profile_id=evidence-research-v1` 和完整 ResearchBrief；缺少其中任一项时不得启用结构化证据模式。
2. Gateway 将 run metadata、所有者和质量配置保存到现有 run 存储。
3. RunJournal 将消息、搜索、页面、工具、Token 和生命周期事件写入现有 SQL `run_events` 表。
4. 主 Agent 正常研究，在最终阶段调用证据研究专用的结构化结束入口。
5. 结束入口接收 `rendered_text`、claims 和 evidence candidates，直接把 `rendered_text` 作为用户可见结果，并把结构化数据写入可持久化 run event。
6. B1 影子调度器在 run 成功后读取 run、持久化 events 和结构化数据。
7. 采集器用系统事实补全和核对候选数据，构建 Evidence Validator 输入。
8. 确定性校验器生成 finding、`auto_status`、`semantic_evaluation` 和 data gaps。
9. 结果继续写入现有 `evidence_validations` 表；异常不改变原 run。

普通聊天、未允许账号和未启用质量配置的 run 不获得结构化结束入口，行为保持原样。

## 7. 组件设计

### 7.1 持久化运行事件

复用现有 `DbRunEventStore` 和 `run_events` 表，不新建第二套事件数据库。

本机验收配置将 `run_events.backend` 从 `memory` 改为 `db`，只保存在 Git 忽略的 `config.yaml`。配置切换需要重启 Gateway。

当证据校验启用但事件后端仍是 `memory` 时：

- 主聊天继续运行；
- 启动日志给出不含敏感数据的警告；
- 校验记录加入 `non_persistent_event_store` 数据缺口；
- 不允许把该结果解释为完成了重启持久化验收。

### 7.2 结构化结束入口

新增一个仅对证据质量配置可见的结束入口，契约名固定为 `submit_evidence_report`。它不是第二个模型，而是当前 Agent 完成任务时提交结果的工具。

输入包含：

- `rendered_text`：最终 Markdown 报告；
- `claims`：核心结论候选；
- `evidence`：证据候选。

可见引用与 Evidence 的关系由 Claim 的 `citation_evidence_ids` 和 `rendered_text` 中的实际链接共同表达，不再增加一份重复映射。

工具必须使用直接结束语义：提交后不能再为了生成最终正文进行一次模型调用。若底层框架无法可靠保证，实施必须停在设计复核，不得静默改成额外模型调用。

结构化事件与最终可见文本必须共享同一 run 和最终消息标识，避免质检到错误版本。

系统为提交结果添加 `schema_version=2.0`，并持久化为 `event_type=evidence.report.submitted` 的专用事件。事件必须包含 `message_id`，同时保存一条用户可见的最终 AI 消息；不能只留下工具结果而让聊天恢复后丢失最终报告。

### 7.3 Claim 候选

每条 Claim 至少包含：

- `claim_id`；
- `text`；
- `claim_type`；
- `dimension`；
- `is_key`；
- `evidence_ids`；
- `citation_evidence_ids`。

Agent 可以声明“候选支持关系”，不能声明人工确认结果。

### 7.4 Evidence 候选

Agent 提交：

- `evidence_id`；
- `source_url`；
- `title`；
- `published_at`（未知时为空）；
- `excerpt`；
- `proposed_relation`：`supports`、`contradicts` 或 `unclear`。

系统补充：

- `canonical_url`；
- `accessed_at`；
- `collection_status`；
- 真实 run、message、tool 和 URL 关联。

Agent 不得提交 `confirmed` 作为最终状态。

## 8. 状态模型

为避免“访问过网页”和“证据确实支持结论”混为一谈，拆成两类状态。

### 8.1 系统采集状态

- `observed`：规范化 URL 能在真实页面访问事件中找到；
- `unobserved`：Agent 提交了 URL，但运行记录中没有对应访问；
- `truncated`：访问事件存在，但内容被截断，无法完整核对；
- `missing`：缺少可关联的页面记录。

### 8.2 人工语义状态

- `pending`：尚未完成人工支持关系复核；
- `confirmed`：人工确认支持结论；
- `conflict`：证据或来源互相冲突；
- `stale`：来源过旧，不能单独支持当前事实；
- `rejected`：不能支持结论。

B1.1 只生成 `pending`，不实现把状态写成 `confirmed` 的人工审批接口。

自动校验可以确认 URL 被访问、摘录可定位和结构完整，但不能把这些系统事实等同于人工语义确认。

## 9. 确定性核对规则

采集器和校验器至少执行：

1. 规范化 URL，移除锚点和常见跟踪参数；
2. 对照真实页面工具事件，计算 `collection_status`；
3. 在已保存页面内容中做规范化后的摘录定位；
4. 核对每条关键 Claim 是否绑定 Evidence；
5. 核对可见引用是否与 Evidence ID 和 URL 一致；
6. 核对当前事实、历史事实、冲突和过期状态；
7. 从系统记录计算字符、搜索、页面、工具、Token 和延迟；
8. 保留重复页面访问事实，同时计算唯一规范化 URL；
9. 对截断、缺失、格式错误和超过事件读取上限分别记录 data gap。

`unobserved` 来源、关键 Claim 无 Evidence、可见引用与绑定不一致应产生 blocker。内容截断或无法自动判断语义支持关系应进入人工复核，不能武断判假。

## 10. Token 与成本策略

B1.1 不设置 Claim 数量、Evidence 数量、摘录长度或结构化输出 Token 的产品硬上限。先通过一个真实样本观察，再由用户决定是否设置阈值。

首个真实样本记录：

- run 总输入、输出和总 Token；
- 模型调用次数；
- 总延迟和估算费用；
- `rendered_text` 字符数；
- 结构化载荷字符数；
- Claim 数量；
- Evidence 数量；
- 摘录字符分布；
- 引用数量和唯一来源数。

系统仍应做来源去重，并自动填写已经掌握的系统字段，避免让模型重复输出。但这些是数据质量和效率措施，不是本阶段的硬性 Token 门禁。

一次启用后的样本只能证明该次总消耗，不能精确证明“新增多少 Token 来自结构化输出”。精确增量需要同任务开关对照，会产生额外费用；B1.1 首轮不执行该对照。

## 11. 异常与安全边界

- 事件写入失败：主回答不失败；校验记录标为数据不完整，不能进入可发布状态。
- 结构化入口未调用：保留最终回答，`semantic_evaluation=not_evaluable`。
- 结构化载荷格式错误：记录字段级 data gap，不尝试从自由文本猜完整结构。
- URL 未实际访问：标为 `unobserved` 并阻断。
- 摘录未找到：若页面内容完整则产生 blocker；若事件被截断则标记无法判断并交人工。
- 质检异常：沿用 `validator_error`，不得修改 run status。
- 权限：沿用 B1 所有者校验；跨用户统一 404。
- 敏感信息：URL 在保存和展示前继续移除敏感查询参数；日志不输出完整工具参数、密钥或用户标识。
- 幂等：同一 run 和同一结构化报告生成相同 report hash，不重复创建记录。

## 12. 验收策略

### 12.1 免费离线契约测试

覆盖：

- 正常 Claim/Evidence 和可见引用；
- 关键结论无证据；
- 未访问 URL；
- 重复和带跟踪参数 URL；
- 完整页面中摘录不存在；
- 被截断页面；
- malformed 结构化载荷；
- Agent 试图提交 `confirmed`；
- 可见“来源 N”与后台 Evidence 不一致。

### 12.2 本机零费用集成测试

使用程序化测试 run，不调用模型，验证：

- `DbRunEventStore` 写入后可读取；
- Gateway 重启后事件仍存在；
- 普通聊天未启用结构化工具；
- 证据质量配置启用结构化工具；
- 结构化结束后没有后续模型调用；
- 影子校验读取同一最终消息和结构化事件；
- 数据缺失时返回 `not_evaluable`；
- 主 run 不被质检失败改写；
- 所有者、幂等和关闭顺序保持正确。

### 12.3 单个真实付费样本

仅当前两层通过并取得新的单次费用授权后执行。验收：

- 可见“来源 N”可点击并打开正确网页；
- run events 跨 Gateway 重启保留；
- Claim、Evidence、引用和真实访问 URL 能对应；
- 校验结果能定位具体 Claim 和 Evidence；
- 记录 Token、调用、延迟、费用和结构体积；
- 人工记录复核耗时及误报/漏报；
- 不自动运行 T002 或第二个样本。

## 13. Go/No-Go

进入单个真实样本前必须同时满足：

- 离线契约测试通过；
- 本机零费用持久化与重启测试通过；
- 结构化结束后无额外模型调用的测试证据存在；
- 普通聊天不受影响；
- 没有提交密钥、完整用户 ID 或本机私有配置；
- 用户重新确认单次付费范围。

真实样本后再决定：

- 是否设置结构化输出或 Token 上限；
- 是否调整 Claim/Evidence 字段；
- 是否增加第二个样本；
- 是否进入人工审批界面和硬门禁。

## 14. AI 产品经理学习结论

B1.1 的核心不是“让模型多输出一个 JSON”，而是建立可追溯的数据责任：

- Agent 提出候选结论与候选关系；
- 系统记录可验证的运行事实；
- 人工承担最终语义确认；
- 指标阈值在有真实观测后设定，而不是事先拍脑袋。

这使后续误报率、复核效率、Token 成本和发布风险都能被真实测量。
